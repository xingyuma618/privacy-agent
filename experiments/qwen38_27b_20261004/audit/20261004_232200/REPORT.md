# 当前合成数据审核

结论：合成流程能生成可解析、可执行的轨迹，MCTS 也确实在做树搜索；但当前 accepted 标记不能直接视为最终合格训练数据。应先修复隐私覆盖检查、补审标注、复核空结果 SQL，再重新筛选现有缓存。此次审核没有修改正在运行的生成代码、配置或训练数据。

## 1. 高优先级：隐私漏检已经进入训练导出

已明确核实两条轨迹保留原始 schema 列名，却得到隐私满分、leaks=[]，而且都出现在快照的训练导出中：

- Prompt / movie_platform__110：外发问题的 Evidence 中仍出现 movie_title、rating_score；例如 `more than val_2 refers to rating_score >val_2`。
- MCTS / movies_4__432：外发 Evidence 仍出现 `keyword_name = 'val_1'`。

这些不是本地 Thought 中合法可见的信息，而是 sql_generate 实际收到的外发内容。按当前系统提示“问题中任何与数据库表、列、值相关的实体都敏感”的定义，它们应被拒绝。

根因：直接检查只遍历教师标注的 entity 表面词；上述标注遗漏了 Evidence 中的原始列名，因此硬检查没有命中，同一个 27B 模型的后续隐私判断也漏掉了它们。当前筛选实现不够严。

独立候选扫描共命中 94 条 accepted 轨迹；其中包含 movie、city 等普通词以及数字，不能把 94 条全部认定为泄露。本报告确认的是上述两条明确列名泄露，不代表其他轨迹都安全，也没有完整验证语义推断攻击。

建议：以完整 schema 和原始问题/evidence 为参照，增加原始标识符覆盖检查；扫描每一次真实外发问题和 schema；对普通词的命中结合实体类型人工或语义复核。过滤不能只依赖同一教师生成的标注和分数。

## 2. 高优先级：实体标注覆盖不足

506 条结构有效标注中，有 273 条存在“原始问题/evidence 出现带下划线的实际 schema 列名，但任何标注 span 都未覆盖”的情况，例如 pub_name、ytd_sales、rating_score。此诊断只检查这一类明确标识符，不是完整 M-R，也不等于 273 条最终轨迹均泄露：智能体可能通过重写删除它们。

但这些标签会用于 entity_extract_train，因此不能仅凭 JSON 可解析、表列存在就作为高质量监督。另有 21 个唯一问题标注失败，主要是把 first, middle, last 等多个列拼成一个不存在的列名。这些被排除，没有直接混入 accepted 数据，但未在本轮自动补标。

建议：标注必须覆盖完整 question + evidence 的所有敏感提及；组合列应拆成真实列实体；对失败和覆盖不足的标注单独补标并保留版本。细节见 annotation_coverage_candidates.json。

## 3. 高优先级：空结果会造成语义错误误接收

480 条 accepted 轨迹全部进行了独立重执行尝试：420 条结果一致，60 条在现有 15 秒上限下超时，没有发现成功执行后结果不一致的样本。超时样本主要集中在 movie_platform，不能因此认定它们错误，也不能宣称它们已通过独立复核。

结果一致仍不是 SQL 语义正确证明。在成功复核的轨迹中，6 条轨迹（5 个唯一问题）的 gold 和预测都为空，发现明确问题：

- MCTS / movie_platform__24：预测输出顺序为 list_followers、user_eligible_for_trial；gold 顺序相反，且 JOIN 条件不同。两边均无行，现有比较只检查列数，无法发现输出列交换。
- MCTS / retail_complains__276：预测用 outcome='Hang'，gold 用 'HANG'。数据库实际枚举为 AGENT/HANG/PHANTOM，SQLite 验证 'Hang'='HANG' 为 false。两边结果为空导致错误值仍被接收。原始 evidence 本身写了 'Hang'，也暴露出输入、标注和最终 SQL 的一致性问题。

不能简单删除所有空结果，正确查询也可能为空。建议给空结果轨迹增加输出列顺序、连接关系和规范值复核，必要时使用额外数据库实例/测试数据验证；超时复核记录单独存放，勿当成通过。

## 4. 训练长度与工具监督需要处理

用学生 Qwen3-4B-Instruct-2507 的真实 tokenizer 和 chat template 检查当前导出：没有模板解析错误，没有重复训练行。Prompt 中位长度 8,026.5 token，MCTS 中位长度 8,133 token；MCTS 有 1 条超过 16,384 token。后续若设置 cutoff_len=8192，将截断相当一部分轨迹，可能丢掉最后的执行验证或 SQL。尚未启动学生训练，当前不是已发生的训练错误。

建议在训练配置确定前优化反复复制的 schema、映射字典，并按最终长度检查和分桶，保留完整工具因果链。学生模型原生最大上下文更长，8K 是潜在训练截断设置，不是模型硬上限。

工具结果回放与真实外发日志匹配未发现异常。另有 8 条轨迹传入 sql_unmask 的映射与本地 canonical map 不同；工具实际忽略传入映射、使用本地 map。这保护执行，但会留下误导性的参数监督，应统一工具接口。Prompt / retail_complains__246 最终 SQL 未在轨迹里调用执行检查，尽管末端独立筛选执行通过，应补强流程约束。

## 5. 符合预期的部分与实验口径

- 快照调用记录的 returned_model 全部为 Qwen3.8-27B，没有发现旧 DeepSeek 或 Qwen2.5-72B 返回记录。
- MCTS 使用的模拟次数为 1–24，平均 8.29；平均节点 14.54，最大 41；平均扩展 4.56，最大 14。这表明确实有多层树扩展。111 个样本用完 24 次预算，应据此评估成本。
- Prompt 115/185、MCTS 214/295 条 accepted 的最终 SQL 与最后 unmask 输出的规范化 AST 不同。部分只是 SQL 写法变化，部分是明确修复；例如 book_publishing_company__170 把 IS NULL 修成 <>0。这符合现有允许自主修复的提示，不能一律判错。但最终 EX 不能直接解释为匿名 SQL 教师首次生成正确，论文应分开统计首次生成和智能体修复后的 EX。
- 工具曾报错后成功恢复的轨迹不应一律删除；应区分有效恢复、超时循环和不完整流程。
- 导出每 100 个完成案例更新一次，快照中的导出行数少于缓存 accepted 数，是正常检查点滞后。最终发布需要完整重新导出。
- 比较生成成本时要纳入共享的 annotation/rewrite 调用，并扣除后端测速暂停造成的挂钟时间膨胀；当前两方法的搜索预算也不相同。

## 建议执行顺序

1. 在新版本中补强外发隐私覆盖检查、标注覆盖检查和组合列格式；保留当前缓存作为原始版本，避免中途混用评分标准。
2. 重新审核/筛选现有轨迹，至少隔离本报告明确泄露、空结果语义错误和未经独立验证的超时样本，再统一重新导出。
3. 确定完整轨迹的训练长度和工具格式，做实际训练数据加载检查后再启动冷启动训练。
